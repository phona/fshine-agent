# 交互契约（什么算"好用"）

> 状态：2026-11-19 初版（验收尺子，不是实现文档；每条标注现状）。
> 最后核对：2026-11-19。
> 上游：`AGENTS.md`（判据红线 / 文档约束纪律）、`docs/architecture/permissions.md`、`docs/architecture/tasks.md`。

业务人员愿意把工作交出去，取决于**省心**：不用盯、不用问、敢信、能接管。下列五条是这份"省心"的可验收表述——每个改动先问它让哪一条更好，答不出来就不做。

## 1. 不打扰：只在需要时出现

- **用户感受**：我不用盯着它。
- **机制**：只发四种消息——受理（带预期）/ 超预期（给"停或等"选择）/ 卡死（建议停或报障）/ 失败·待确认（给动作）。**每条必须带一个用户能做的动作**；进度、步数、检查点一律不报；群聊不主动。
- **怎么验**：10 分钟内零主动消息；超 10 分钟恰一条且含「停下来」「继续等」；30 分钟后不再自动发。
- **现状**：机制与生产接线已实现（`packages/agent/src/task-runner.ts` 两档阈值 + 落库幂等；server 注入 `createLongRunningNoticePort`：只 1:1、只 live、走既有 `sendText`）。扫描补拍已修：本趟刚认领的任务原先错过扫描就再也不扫（超时提醒发不出去），现在认领后补一个扫描节拍（`apps/server/server-long-running-notice.test.ts` ①，反向绊线已验证）。"唤醒回合让模型自己说"未做。

## 2. 有预期：先说大概，再兜底

- **用户感受**：心里有数，不用反复问。
- **机制**：受理回执给「大概 X 分钟」（执行层 `est_seconds` 累加作锚点，必须带"大概"）；超预期由第 1 条的兜底接住。
- **怎么验**：回执含估算与"大概"；无估时只能说「办完发你」，不得编时间。
- **现状**：文案已实现（`backgroundTaskReceiptNotice`），仅异步派发下出现；生产面已 async（有推送面即 async），回执可达。

## 3. 可查可接管：白盒但不刷屏

- **用户感受**：随时能接管。
- **机制**：`task_status` / `task_result` 随时可查；取消给带业务名的回执（"已请求停止 / 已停止 / 没停成"）；状态不主动推送。
- **怎么验**：问「跑哪了」能答；说「停」能停或如实说停不下来（不得假装）。
- **现状**：查询与取消已有；步骤级白盒（执行层报的 phase）未做。

## 4. 结论有据：不编、不粉饰

- **用户感受**：敢信。
- **机制**：运算交给代码（执行层聚合字段优先）；失败/未知如实说；**部分完成逐条报**（"完成 X、未完成 Y"）；`result_unknown` 不自动重放。
- **怎么验**：聚合必须可溯（E15 `aggregate.source`）；失败不冒充成功；未知时停下交用户核对。
- **现状**：聚合来源与失败话术已实现；逐条结果已落地（契约 v4 的 `completed.items`，partial 不得说成成功）。

## 5. 分工透明：用户永远不需要懂

- **用户感受**：我只说事。
- **机制**：Main 拆包、Worker 执行、执行层拥有业务规则与事务；用户可见文本不出现内部术语（operation 名、任务编号、执行层、uuid、绝对路径）。
- **怎么验**：用户可见出口过内部术语黑名单（`packages/agent/src/notification-render.ts`）与路径剥离（`packages/agent/src/server-paths.ts`）；拒绝话术不含 operation 名。
- **现状**：黑名单与路径剥离已有；受理回执已去编号。

## 不做什么

不报进度/步数；不做任务面板；不在群里主动说话；不用词表判语义；不为长活造第二套框架。
