# fshine-agent 架构

状态：**目标架构**。当前实现与它的差距见 §10；未完成项在那里列明，不在正文里假装已存在。

---

## 1. 定位

fshine-agent 是**编排运行时**，不是财税系统。它把用户的自然语言请求变成受控的平台执行，并把结果呈现回来。**它不拥有任何业务口径。**

整个系统分两层：

```text
┌─ 编排层（fshine-agent）────────────────────────────────┐
│  领域无关。增加一个新业务域时，这一层一行不改。          │
│                                                        │
│  持有一份「业务 skill」——只含程序性知识（§5），          │
│  用于长任务拆解与信息补齐，不含任何执行口径。            │
└───────────────────────┬────────────────────────────────┘
                        │ 领域无关的委派契约（§4）
                        ▼
┌─ 业务执行层（每域一套，可插拔）─────────────────────────┐
│  17dz-platform 是第一个。                              │
│  提供：SKILL.md（口径与事实）、operation 清单与估时、    │
│  计划门、执行端逐次校验、累计账本、以及自己的记忆。       │
└────────────────────────────────────────────────────────┘
```

### 分层的判据

三条判据，失败半径互不重叠——这是分层的全部收益：

> - 删掉**编排层业务 skill** 里任意一条 → 编排变笨，**不会产生错误数据结论**
> - 删掉**编排层长期记忆** 里任意一条 → 交互体验变化，**不会产生错误数据结论**
> - 删掉**执行层 SKILL / 记忆** 里任意一条 → **可能直接把事情做错**

编排层因为不懂口径，所以它**没有能力产出错误结论**——它只能派错单，而派错单会被执行层挡回来或报错。这就是为什么值得分层：不是保证知识永远一致，而是保证不一致时代价可控。

## 2. 编排层职责（冻结清单）

加新业务域时，以下十条一行不改：

| # | 职责 | 说明 |
|---|---|---|
| 1 | 渠道、身份、会话 | 企微接入；principal 由可信用户 ID 解析 |
| 2 | 上下文装配 | Conversation Log / Context State / 主动回溯 |
| 3 | 指代消解 | 只用**机械来源**：当前消息、Log 里的实体、平台自己返回的响应 |
| 4 | 回合分类 | `conversation` / `delegate` |
| 5 | 长任务拆解与派单 | 凭业务 skill 的**程序性**知识 |
| 6 | 任务计划状态维护 | 第几步、每步结果、失败重试 |
| 7 | 长期记忆维护 | **仅**用户偏好与稳定事实，不含领域内容 |
| 8 | 通用闸口 | 预算 / 通知 / 确认 / 执行凭证 |
| 9 | 领域无关校验 | 计划里的每个实体必须能在「当前消息 / 检索证据 / 本轮平台响应」里逐字找到 |
| 10 | 出口规则 | 回复含数字结论 → 必须本轮有执行凭证 |

**第 3 条的边界**：实体消解（简称→全名、歧义→候选）归执行层，它有目录查询能力。编排层只做"从已知文本里把实体取出来"，不做"猜这个实体是谁"。

**第 9 条不需要领域知识**：宿主不需要知道"幻辰财税"是不是账套，只需要做字符串包含。而"本轮平台响应"这一项很关键——执行层调目录查询拿到唯一候选，那个候选就是合法解析出来的。

## 3. 两个 Agent 的分工

```text
Main Agent = 规划者          Subagent = 执行者
  知道：任务类别、依赖关系       知道：参数、口径、红线
       每类必须的信息                 怎么做这一步
  做：  拆解 → 派单 → 收结果      做：  执行一步
       出错时与用户/执行层交互            成功 → 返回结果
  不做：产出任何数据结论                失败 → 返回原因和所需信息
                                  不做：跨步规划、自行扩大范围
```

**纠错环是有意设计的**：Subagent 执行不了就报错回来，Main Agent 重新拆解、追问用户、或换步骤。它让知识漂移从"致命"降级为"多问一句"。

Main Agent 依然不能产出财务结论——它只能编排。出口校验（§2 第 10 条）一动不动地守着。这比把执行工具直接还给 Main Agent 安全得多。

## 4. 委派契约

Main Agent 每回合先申报一次：

```ts
route_current_turn({
  kind: 'conversation' | 'delegate',
  request: string,              // 加工后的用户请求
  continueTaskId?: string,      // 仅在补充子 Agent 索要的信息时使用
})
```

**三个字段，零业务知识。** 没有 `taskType`、没有 `accountQueries`、没有 `periods`、没有 `accountResolution`——那些都要求编排者做领域判别（区分账套名/科目名/客户名、知道凭证必须带期间），正是知识污染的来源。

`request` 需要加工，这是编排层的核心价值，而且加工全是机制：

| 用户说 | 加工成 |
|---|---|
| 这个账套 202608 呢？ | 「查询新兴五金账套 202608」（实体从 Log 取） |
| 那把 202607 也看一下 | 「查询新兴五金账套 202607」 |
| 继续 | 「继续 task_xxx：<子 Agent 上次索要的信息>」 |

宿主持做的确定性的事：校验申报结构、记录执行凭证、出口拒绝"委派了却零执行"的回复。

## 5. 业务 skill（编排层持有）

### 内容边界

**只含程序性知识**：这是什么任务、拆成几步、每步需要什么信息、步骤之间什么依赖。
**不含口径性知识**：什么能算什么不能算、什么参数必须带、结果为空怎么办。

### 草案

```markdown
# 财税业务编排知识（fshine-agent）

## 用途
只用于长任务拆解与信息补齐。不含任何执行口径——"怎么做是对的"归执行层。

## 任务类别与拆解
| 类别 | 拆解 |
|---|---|
| 单点余额 / 单点凭证 / 账套检索 | 1 步 |
| 跨账套核对（N 个账套同一口径） | 按账套拆 N 步，互不影响，最后汇总 |
| 跨期间对比（1 个账套 M 个期间） | 按期间拆；或先问执行层能否一次返回 |
| 凭证录入（写） | 1 步，但必须经用户确认后才执行 |

## 每类必需信息（缺则问用户，不要猜）
| 类别 | 必需 | 可缺省 |
|---|---|---|
| 余额 | 账套 | 科目（默认应收）、期间（默认当前） |
| 凭证 | 账套、期间 | — |
| 检索 | 关键词 | — |

## 拆解原则
- 一步只做一件可独立成败的事
- 任一步失败不阻塞其他步，汇总时如实报告失败的那几步
- 只有用户明确说"全部/各/逐个"才拆多步；否则先按单步派单，
  执行层回报需要扩大再议
- 不要为了"顺手"把无关账套或期间并入某一步
```

这份 skill 很小（约 400 字），而且**没有任何一条"怎么做是对的"**。它是一张地图，不是执行手册的副本。

## 6. 三类记忆

| | 编排层（fshine） | 执行层（17dz） |
|---|---|---|
| 存什么 | 用户偏好、稳定事实、任务计划状态、会话上下文 | 客户录入格式差异、录汇票规则、历史口径 |
| 用来 | 决定**怎么交互、怎么拆解、怎么呈现** | 决定**怎么把这件事做对** |
| 跨域有效 | 是 | 否 |
| Main Agent 需要理解 | 是 | **完全不** |

执行层的记忆归执行层自己存储和使用。编排层不存、不转发、不理解。用户说"跟上次一样"时，跨任务的口径记忆在执行层那儿，它查得到，不需要编排层转手。

## 7. 执行层必须提供什么

```text
SKILL.md          领域口径与事实（子 Agent 提示词的来源）
operation 清单    名称、参数、est_seconds（权重）、access/effects
计划门            plan evaluate / activate / status
执行端            逐次校验实际调用 + 累计账本（跨进程、重计划不清零）
自己的记忆        领域性、按客户/账套等维度持久化
```

子 Agent 的系统提示词由执行层提供。编排层只保留框架性的一句：你是被委派的执行者，你的回复会直接展示给最终用户。

## 8. 通用闸口（编排层与执行层各占一半）

```text
Main Agent 申报 delegate
      │
      ▼
宿主附加可信身份 / 任务 ID / 计划版本（不可由模型填写）
      │
      ▼
执行层计划门：execute / notify / confirm / stop
      │
      ├─ execute  直接执行，累计计量
      ├─ notify   宿主先把范围与预计耗时发给用户，确认送达后才激活
      ├─ confirm  暂停，等用户真实回复；确认绑定用户 + 计划版本 + 有效期
      └─ stop     达到硬上限，带明确原因码
      │
      ▼
执行端逐次核对：脚本、实体参数、剩余预算
      │
      ▼
宿主记录执行凭证 → 出口校验 → 用户可见回复
```

- **notify 的送达是激活授权的一部分**：没送达成功就不激活。
- **模型自报的确认字段不是凭据**：激活密钥由宿主持有，只在激活子进程短暂注入，worker 环境主动剥离。
- **重计划不重置累计用量**；同一任务的 notify 次数和重计划次数都有上限，反复试探会被升级为必须等用户确认。

## 9. 安全边界

- principal 由可信的企微用户 ID 解析，模型不得改变用户身份或授权配置。
- 工作目录与 skill 路径只来自部署配置，启动前 realpath 校验。
- credentials 不经用户消息或模型参数传递。
- Main Agent 不直接执行平台命令；命令与脚本选择由执行层约束。
- 只读计划才能过计划门；写操作继续走服务端两步确认。
- 审计不写 API key、密码、未授权数据或完整页面内容。

## 11. 明确不做

MCP server/host、通用多 Agent registry、跨域结果聚合、调度与浏览器人工接管。长期记忆的定时生产调度与 `MEMORY.md` 落盘仍在范围外。
