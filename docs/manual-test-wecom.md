# 企微端手工测试指南

目的：验证真实企微收发、宿主与执行层 worker 的委派、多轮恢复和回答质量。执行层返回的结果会变化，数值只要求与本次查询结果一致。

> **大部分行为断言已经有离线全链 e2e 覆盖**（`tests/e2e/turn-loop-*.test.ts`，把消息直接注入与企微相同的 handler 链路，不起企微连接；其中报错回路在 `turn-loop-needs.test.ts`）。标 ✅ 的用例跑 `npm test` 即可，不需要在企微里手工发消息；本文档剩下要人工做的是**真实收发、Markdown 渲染和真实数据口径**。映射见 §8。

## 0. 前置检查

| 项 | 方法 | 通过标准 |
|---|---|---|
| 服务存活 | 查看服务进程 | 进程存在；日志有启动标记 |
| 企微连接 | 查看服务日志 | 已认证、心跳正常，没有重连风暴 |
| 执行层配置 | 检查 `config/agent.yaml` | `contextProfiles.<profileId>.root` 指向可用的执行层根路径；`.agents/skills` 可读 |
| 主账号 | 使用配置的企微用户 | principal 已启用，测试数据在其可见范围内 |

测试阶段不要同时运行第二个机器人连接，避免企微单连接互踢。相同用户和会话的消息应串行处理。

## 5. 通道能力

| # | 操作 | 预期 |
|---|---|---|
| 5.1 | 发送：`发个测试图片` | 收到图片通道演示；文本说明为模拟数据 |
| 5.2 | 触发较长回复 | 企微正常渲染，无 JSON、堆栈、绝对路径、task 内部字段泄漏 |
| 5.3 | 发送：`记住：我偏好简体中文简洁回答`，后续另开对话再问偏好 | 后台低频整理带来源长期记忆；偏好可用于表达，查询结果/对象不能作为长期授权 |
| 5.4 | 先聊一个较宽范围，再发起新的单次查询并说“继续刚才的对账口径” | 宿主可用 Context State/历史检索理解指代；旧范围作为资料，不自动绕过计划重量通知 ✅ |
| 5.5 | 在群里 @机器人 发送查询 | 剥离开头 @ 段后照常处理；@ 之后的正文才是用户请求 ✅ |

## 6. 失败排查

1. 回复“查询失败/请稍后再试”：查看服务日志中的错误标记、超时标记或降级回复标记，确认 LLM 配置、执行层根路径和 Skills 路径可用。
2. 回复“需要登录处理”：按执行层对应 Skill 的登录流程检查运行环境；不要在企微消息中传递密码。
3. 子 Agent 没有执行领域脚本：确认宿主是否调用委派工具、任务 request 是否完整，以及执行层根路径配置是否正确。
4. 任务无法继续：确认 task ID 属于当前 principal 和 conversation；不要手动复用别的会话的 ID。
5. 重启服务：停止旧进程后重新运行启动命令，再从新会话开始测试。

## 8. 验收入口

### 8.1 离线全链 e2e（`npm test`，不需要企微连接）

`tests/e2e/turn-loop-*.test.ts` 把消息直接注入与企微相同的 handler 链路：
假 SDK 发一条企微文本帧 → 真实 `WecomBotChannel` 适配器 → `createServerReplyHandler`
→ `createMessageHandler` → `createTaxAgentRuntime` → 真 spawn 的执行层网关
（plan evaluate/activate/status、累计账本、HMAC、逐次参数绑定、mock executor）。
共享替身在 `tests/e2e/harness.ts`，多个文件按主题拆分、并行执行。

只有两样是假的：**模型**（宿主与子 Agent 用脚本化驱动回放）和**执行器**
（`EXECUTION_EXECUTOR=mock`，由执行层平台自己读，宿主不读它）。企微投递语义、计划门禁、
跨进程账本全是生产代码。

```bash
npm test -- tests/e2e/turn-loop
```

### 8.3 仍需人工的部分

- 真实企微收发、长连接稳定性、Markdown 渲染（5.2）
- 真实执行层返回结果的查询一致性与金额一致性
- 写操作两步确认的真实落账（归执行层仓库持有：写授权/拒绝由执行层自己的门给出，
  编排层不再持有 `FSHINE_REAL_COMMIT` 那道闸——2026-11-08 裁定，见文末「已移出事项」）
- 真实模型下的委派合规率：日志关注 `turn_declaration`、`route_declaration_missing` 与 `reference_evidence_injected`（宿主主动回溯的注入条数/截断）

### 8.4 文件消息的气泡归属（文件收据波，mock 证不了）

mock 的 `replyStream` 是个数组，既不会转圈也不会拒收，所以下面三条只能真机验：

1. **发 2 个文件、不发指令** → 约 2 秒后出现**一条**合并收据（「已收到 2 个文件：a、b」，不带「等待你的指令」后缀），且两个文件消息底下**都没有**转圈的 spinner、没有「收到,正在处理…」。
2. **紧接着发一条指令** → 只有指令那一个气泡里带收据（「已收到 2 个文件：a、b」，无「等待你的指令」），收据在全链上只出现一次。
3. **只发 1 个文件就发指令** → 收据由指令回合带，文件消息底下无残留 spinner；并窗（2s）短于渠道被动回复时限——若收据迟迟不出现或出现时报 `846608`，说明这个上界判错了，先核 `RECEIPT_COALESCE_MS`。

同一场景的追问复用 `conversationId`，每条消息使用新的 `messageId`。验收存档至少包含
`requestId`、主会话、`taskId`（如有）、子 Agent 执行结果和最终回复。不要要求或留存 MCP
trace、原始 JSON 或平台密码。

### 8.5 乱序到达的等待与迟到文件（乱序到达波，mock 证不了）

乱序是**投递层**的事，mock 的替身按调用顺序同步投递，模拟不出来。下面三条只能真机验。

1. **文件跨 3 秒落地 + 一条指令**（用户实测的形状）：发 2 个文件，隔约 3 秒发第 3 个文件，
   紧接着发指令。预期：指令回合的收据列出**全部 3 个**文件名（宿主会等 burst 稳了才派单，
   上界 8 秒），且那一轮用的是齐的那一批。若只列出 2 个，说明稳定器没起作用——先核
   `waitForBurstSettle` 是否被 `FSHINE_INBOUND_DEBOUNCE_MS=0` 关掉了。
2. **迟到文件的单条收据**：指令回合已经开跑之后，再发一个文件。预期：约 2 秒后出现**一条**
   合并收据（「已收到 N 个文件：…」，无「等待你的指令」后缀），且**不出现**「上一条指令已经处理完了」
   这类话术（乱序之下那不是异常，且回合可能还在飞，那句话会是假的）。
3. **迟到文件不丢**：接第 2 条，再发一条指令（例如「把文件补上」）。预期：那一轮的首帧
   收据包含迟到的那批文件，且它真的被用上（终稿应体现，而不是「没有数据」）。

同批注意：`FSHINE_INBOUND_DEBOUNCE_MS` 未设时默认 2000（一个窗口），稳定器最多 4 个窗口；
置 0 会连稳定器一并关掉，退回到「固定不等待」，第 1 条会红。

### 8.6 重复请求真的重新执行（重复请求波，mock 证不了"模型选了哪一枝"）

mock 的 Main Agent 是脚本化驱动，`route_current_turn` 申报什么由脚本定——它证得了"宿主接到
conversation 申报时会退回重填"，证不了"真实模型在重复请求上到底选哪一枝"。下面三条只能真机验。

1. **同一条指令连发两遍，第二遍必须真的重新执行**：发「帮我发一下文件型结果给我」+ 结果
   文件，等它跑完并回传文件；**原样再发一遍**（同样带文件）。预期：第二遍**重新委派**（日志有新的
   `turn_declaration kind=delegate` 与新的 `delegation_span`，不是 `repeat_request_declaration_bounced`
   后仍停在对话枝），并**再次回传文件**。若第二遍只回文字、没有新文件，先看日志：有
   `repeat_request_declaration_bounced` 说明宿主退回去过而模型仍选了 conversation（放行是设计内的
   退化，见 change-safety §11）；连这条事件都没有，说明宿主没判出重复（核转录里那一轮的回执形态）。
2. **第一遍停在闲聊时，重复闲聊不被打断**：发「在吗」→ 等回复 → 再发「在吗」。预期：第二次正常
   对话，日志**没有** `repeat_request_declaration_bounced`（早前那一轮没有委派痕迹，不该被判成重复
   任务请求）。
3. **终稿里不出现服务器路径**：接第 1 条，第二遍的终稿（以及任何一轮的终稿）里**不应**出现
   `tmp/…` 或 `/home/…` 形式的路径；文件名、人数、金额照旧齐全。若看到路径，日志里会有一条
   `server_path_leak`（宿主删过它并留了痕）——看到路径却没这条日志，说明有未登记的路径形态漏过
   判据，把原文贴回仓库。

### 8.7 进度帧里不再出现服务器路径（进度帧路径波，mock 证不了"用户眼前的气泡流"）

单测与 e2e 钉的是帧的**文本**与**有无**（`serveGateStepText` 探到路径不发帧、`describeKeyArgs` 不放
路径型取值），钉不住用户在客户端看到的气泡流。下面三条只能真机验。

1. **带 `--out-dir` 一类路径参数的调用，帧里不再有路径**：重跑一次文件型结果类任务。预期：「正在…」帧只到 label 为止（如
   `正在处理数据源 + 契约草稿…`），**不出现** `tmp/…`、`task_…`、`/home/…`；帧数不因少了参数
   而变少，也不出现空帧。
2. **审计里仍查得到完整命令**：帧变短不等于信息丢失——同一次调用的平台审计 detail 仍带完整命令原文
   （`--out-dir tmp/task_<uuid>` 在里面）。排查时以审计为准，不以帧为准。
3. **终稿与帧两条出口都不再漏**：接 §8.6 第 3 条——任何一轮的终稿与任何一帧里都不应出现服务器路径。
   若帧里看到路径，说明这一波三个合成点有漏（把帧原文贴回仓库，优先核是不是新的帧来源没走
   `serveGateStepText` / `renderToolStepText`）。

### 8.8 收据文案与终稿点名（交互缝波，mock 证不了"用户读起来像不像催命"）

单测与 e2e 钉的是帧的**文本**（孤儿收据不带「等待你的指令」、终稿尾部带「本轮回传：\<文件名\>」），钉不住用户读到它的感受。下面三条只能真机验。

1. **只发文件、不发指令**：约 2 秒后文件消息底下出现**一条**收据「已收到 N 个文件：a、b」，**不带**「等待你的指令」。若你觉得少了那句反而不知道要发指令，把会话贴回仓库——那是文案判断，不是机械判据，改起来是一行，但要有真实反馈才改。
2. **带指令的回合**：收据只在**本轮真有新文件**时出现（只说一次、只列新到的那几个）；终稿尾部有「本轮回传：\<文件名\>」一行，紧跟其后的是那个文件本身。若终稿为空（委派没说话），那一行就是全部文本——不应出现"只有一个文件消息、没有任何文字"的形状。
3. **与附件无关的后续回合**：发过文件之后再问一句别的（例如「发一下某个文件给我」），那一轮**不出现**任何「已收到 N 个文件」；首帧是「开始处理你的请求」。这是 D-110 修掉的复读，真机上确认它没有以别的形态回来（例如并窗晚到、或披露帧换了个说法）。
