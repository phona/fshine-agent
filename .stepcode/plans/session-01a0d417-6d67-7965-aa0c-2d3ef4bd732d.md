# 修正方案：先对齐问题与架构，再谈改动

> 这份文档分两半：前半是**问题对齐**和**架构还原**（确认我们聊的是同一套东西），后半才是改动。
> 核心论断先说：**这次碰到的故障不在多层 reduce 层，而在 reduce 管不到的执行授权层。** 所以方案是补一层，不是改 reduce。

---

## 一、我们要解决的问题（对齐）

按"是不是上下文管理问题"分两组。

### A 组：不是 reduce 层的问题——执行链可以被绕过

**A1. Main Agent 能拿旧上下文直接回答实时查询，整条执行链形同虚设。**

这是总根因，三次实测都命中：

| 时间 | 现象 |
|---|---|
| "帮我查一下幻辰的应收账款还有多少" | 13.3 秒回复，**零 17dz 调用**，直接引用旧会话口径；后台 Context State 抽取还超时回退了 |
| 14:59 重复提问 | **没有任何委派、没有计划、没有平台调用**，Main Agent 直接复制 14:36 的旧答复 |
| "猫一杯" | 199 秒、11 次 mock 调用，把旧对话的幻东/幻辰带进新任务 |

性质：Context State 和历史检索都在正常工作，但**"本轮是否必须产出真实执行结果"没有任何东西保证**。计划门禁只能管"已经进入执行链的调用"，管不住一条根本没进执行链的回答。

**A2. 旧任务范围渗入新问题。**

Context State、recent turns、history tools 都把旧内容以"历史资料"身份送进 prompt，防渗入靠的是**标签和提示词**，不是结构隔离。`state_recent` 默认还把最近 2 回合原始 assistant 文本（含旧财务数字）原样递回去。

### B 组：是 reduce/闸口层的问题

**B1. 预算内反复试探，通知不拦截。**

17dz 的重量闸只算**累计重量**（calls/seconds），算不出"范围扩张次数"和"任务类型错配"。`notify` 档（默认 ≤10 次调用）只通知不拦截，11 次试探调用全部放行；用凭证查询回答余额问题也不是重量问题，闸口看不见。

**B2. 确认状态机不收尾。**

`ConfirmationMatchResult` 没有 `superseded` 状态，`handler.ts` 也没有对应分支。旧计划被新计划取代后用户发"确认继续" → 平台 `PLAN_NOT_PENDING:superseded` → 被包成普通 Error → 用户只看到 generic"处理失败,请稍后再试"。

### C 组：工程质量（不解决就没法继续验证）

- 工作区**不可运行**：`runtime.ts:13` 导入的 `routeTaskIntent` 不存在，`tsc` 报 TS2724，`runtime.test.ts` 3 条用例挂；`main.ts:123` 无条件传 `intentDriver: driver`，线上每条消息都会走到死代码。
- 测试断层：唯一真起 17dz CLI 的 `tests/e2e/plan-awareness.test.ts` 是 `describe.skipIf(!platformRoot)`，**默认整个跳过**；`scripts/acceptance.ts:276-282` 没传 `intentDriver`，和生产装配不一致。
- 文档跑偏：`docs/v0-architecture.md` 把"Semantic Intent Router"写成了当前基线。

## 二、架构还原：多层 reduce 管上下文，TaskScope 管授权

### 2.1 上下文管理层（多层 reduce，已基本落地）

```
                      Conversation Log
                   （append-only，唯一事实源）
                      ▲   ▲   ▲   ▲
   每轮交互结束 ───────┘   │   └────── 较低频率 consolidate
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
     ┌─────────────────┐      ┌──────────────────┐
     │ Short-term      │      │ Long-term        │
     │ Reducer         │      │ Reducer          │
     │ C(t)+events     │      │ 稳定候选          │
     │   → C(t+1)      │      │   → 提炼          │
     └────────┬────────┘      └────────┬─────────┘
              ▼                        ▼
       Context State            Memory Records
     （工作记忆 / 投影）      （带 source_event_ids）
              │                        │
              │                        ▼
              │                  MEMORY.md
              │               （长期投影，非数据库）
              ▼
         Main Agent ◄──── History Tools（按需回溯）
              ▲
     system + current message
```

四条不变量，是我判断"落地对不对"的标尺：

1. **投影不能取代事实。** Log 是 source of truth，Context State 是 working projection，MEMORY.md 是 long-term projection。Reducer 只能生成投影。
2. **禁止 summary-of-summary。** 长期记忆底层必须是带 `id/type/content/source_message_ids/status` 的 records，`MEMORY.md` 只是可读投影——否则 MEMORY v1→v100 之后无法分辨哪句是用户说的、哪句是第 37 次 reducer 自己概括的。
3. **Reducer 产物必须带证据。** 每条 note 附来源事件 ID，可逐字回溯；`decisions` / `hypotheses` / 用户明确事实要分开。
4. **历史从"自动进上下文"变成"可按需查的数据源"。** 回忆是显式动作，可 trace；检索回来的内容只是历史资料，不构成当前授权。

**落地情况：这一层基本做到了。** append-only Log、语义抽取（带逐字引文校验）+ 确定性兜底、按会话串行不阻塞回复、三层记忆过滤（抽取正则 / 归约冲突 / 存储乐观并发 CAS）、`MEMORY.md` 刻意只做渲染字符串不当证据——都在。

### 2.2 执行授权层（不在 reduce 体系内）

```
   对话 ──► TaskScope（目标/账套/期间/来源/版本，服务端维护）
                  │
       Agent 提交执行计划草案
                  ▼
      17dz 确定性预算评估器 ── execute / notify / confirm / stop
                  ▼
       执行门逐次核对实际调用（累计不清零）
```

关键约定：**TaskScope 不能由任何 reducer 授权。** Context State 回答"用户在聊什么"，TaskScope 回答"这轮工具实际获准查什么"。用户一开始就要求查全年 → 按重量管理；Agent 中途自行扩大 → 必须让用户感知。

**落地情况：重量账本、四档决策、HMAC 激活、逐次参数绑定都做到了。** 缺的正是最上面那一格——**"本轮授权"从哪来**。现在它是隐式的：Main Agent 自己决定要不要委派，宿主不记录、不校验。

### 2.3 仓库边界

`fshine-agent` = agent runtime（企微、会话、上下文、调度、通用预算钩子）；`17dz-platform` = 财税业务策略（计划评估、TaskScope 业务字段、执行端逐条校验、累计账本）。业务规则不放 fshine。

| 问题 | 所在层 | 现状 | 修法 |
|---|---|---|---|

## 四、方案设计

### 4.1 回合契约（TurnContract）—— 把"本轮授权"变成显式、可校验的东西

Main Agent 的工具面只给两个：`route_current_turn` + history tools。**不再给 `run_17dz_task`，也不再要第二个路由模型**（零额外模型调用，语义判断仍归 Main Agent）。

宿主在 `exec` 里就地处理：

```ts
if (tool === ROUTE_CURRENT_TURN_TOOL_NAME) {
  const intent = validateTaskIntentEvidence(parseTaskIntent(JSON.stringify(args)), userMessage, context);
  if (intent.kind === 'clarify') throw new ToolUserError(intent.question);   // terminate → 宿主追问
  if (intent.kind === 'platform_query') {
    const result = await deps.platformTask.run({ request: userMessage, taskIntent: intent }, { trusted: ctx }, signal);
    turnExecution = result.execution ?? null;                               // 见 4.2
    throw new ToolUserError(result.text.trim() || FALLBACK_FAILURE);        // terminate → 本轮真实结果
  }
  return { recorded: 'conversation' };                                      // 继续普通对话
}
```

复用已有机制：`ToolUserError` 从 `exec` 抛出 → `pi-driver.ts:324` 的 `terminate:true` → 该文本成为本回合最终回复，不再喂回模型。不需要新造中断协议。

**为什么撤掉语义路由（那个独立的第二个模型）——写在这里，防止半年后有人又加回来：**

- **它不解决根因。** 路由器也会误判；判成 `conversation` 而用户其实在问实时数据，就回到同一个故障，还多花一次模型调用的延迟。14:59 那次重复提问就是活证据：路由当时已在跑，Main Agent 照样直接复制了 14:36 的旧答复。
- **它让上下文少的模型替上下文多的模型做判断。** 路由器只看当前消息 + 近期上下文，Main Agent 看全套；同一个判断，后者反而要听前者的。
- **它用模型干一件"契约 + 确定性校验"干得更好的活。** 路由只决定走哪条路，出口的"无执行凭证不外发"才保证没查就不能答。后者无论如何都得有，前者可选——为了可选的那个牺牲正确性，还多付一次调用，不划算。

**它确实买到的一样东西要留**：它把"本轮授权"这个一直没有名字的洞捅出来了，`TaskIntent` 那套带证据的结构化声明也是这时候成形的。产物留（`task-intent.ts` 已有且带单测），但改由 Main Agent 自己在同一回合产出，宿主只负责校验。

三条性质：

- **证据校验是 fail-closed 的**：`validateTaskIntentEvidence` 已实现——账套/期间/搜索词必须逐字来自当前消息，`referenced` 必须能在上下文唯一解析，否则降级为 `clarify`。这就是 A2 的结构性保证，且不靠正则猜意图。
- **范围校验链保留**：`validatePlanAgainstTaskIntent` 继续在 `pi-coding-driver.ts:230-236` 生效，因为 `taskIntent` 现在来自 `route_current_turn` 而不是第二个模型。
- **意图进了 Log**：route 工具的 toolResult 会作为 `tool_result` 事件落库，可回溯。

### 4.2 执行凭证（TurnReceipt）—— 宿主的硬兜底

```ts
// TurnDriverResult 增加
execution?: { planId: string; version: number; calls: number };
```

`pi-coding-driver.ts` 用闭包里已有的 `activePlanId`（补 version）在返回时带上；`context.ts` 的 `SubagentTaskResult` 透传；`runtime.ts` 记为本回合变量。

### 4.3 出口校验（唯一的硬规则）

```
contract.kind === 'platform_query'
  && receipt == null
  && pendingPlan == null
  → 不外发模型文本，替换为确定性澄清：
    "我需要实际查询平台才能回答这个问题，但本轮没有产生任何平台查询。
     请告诉我要查的账套和期间，我重新查一次。"
```

- 允许 `pendingPlan` 例外：计划停在确认门是合法终态，用户确认后走 `resumeTaskId` 路径，那条路径天然带执行结果。
- 不需要判断"回复是否像澄清"：`not_found`（账套不存在）**有**执行痕迹（`finance.search-account-sets` 真跑过）。没有凭证又宣称回答了财务问题，一律按未执行处理。

### 4.4 跳过申报的处理

1. 第一次：宿主记 `declared === false`，丢弃文本，追一条 user 消息重跑一次。
2. 第二次仍跳过：fail-closed，返回 4.3 的确定性澄清，**绝不外发模型文本**。

残余风险（模型误判为 `conversation`）只能靠证据校验 + `task_intent_route` 结构化日志压住，不引入第二个模型。这点记为已知限制，靠日志统计误判率再决定要不要调 prompt。

### 4.5 recent turns 打历史资料标签

`selectRecentTurns` 的产出只进模型上下文、不落库，可安全改造：给最近 N 回合的 assistant 消息前置

```
【历史资料：上一轮的回复，可能已过期；不得作为本轮实时结果引用】
```

不判断内容是否"像财务数字"——那是模糊匹配，正是上次被否掉的方向。

### 7.1 三条硬规矩（针对"验收测试跑过了，一测问题还在"）

1. **已复现故障的回归测试必须落在真实跨进程链路上。** 真 `spawn bin/17dz`、真 plan 账本文件、真 HMAC 激活、真累计记账；mock executor 只替掉浏览器和网络。**不允许只用内存 `fakeCli` 断言"传了什么参数"**——那验的是接线，不是行为。上次 237→246 项全绿但企微一测就崩，根因就是跨进程语义只剩一个默认跳过的 e2e 在管。
2. **不允许 `describe.skipIf` 静默跳过。** 环境不满足就显式失败并说明缺什么，而不是让 CI 一片绿。
3. **每条回归先红后绿。** 先在当前代码上跑出红（证明它真能复现故障），再改实现。写不出来红的，说明这条验收是装饰。

### 7.4 企微 mock 手测（人肉最后一道）

| 场景 | 预期 |

### 7.5 离线全链 e2e：直接发消息给 fshine-agent，不手工点企微

**这是本次最重要的基建。** 现在的验证方式是"改完 → 重启 mock 服务 → 你在企微发消息 → 我看日志"，每一步都要人肉，而且回归只能靠你当测试器。要有一条能进 `npm test` 的链路：**造一个假的企微 SDK，把消息直接灌进生产装配，断言用户最终会收到什么。**

#### 装配抽取（前置改造）

`apps/server/main.ts` 现在是过程式装配，driver 在内部创建，测试换不进去。抽成：

```ts
// apps/server/assembly.ts（新增）
export function createServerAssembly(overrides: {
  driver?: TurnDriver;              // Main Agent 驱动
  workerDriver?: TurnDriver;        // 17dz 子 Agent 驱动
  platformRoot?: string;
  env?: NodeJS.ProcessEnv;
}): { channel, handler, store, runtime, planConfirmation }
```

- `main.ts` 只传真实 driver（行为不变）。
- `scripts/acceptance.ts` 改用同一函数——**顺手消掉"验收脚本和生产装配不一致"这个老问题**（现在它没传 `intentDriver`，Phase 1 后连这个字段都没了）。
- e2e 传**脚本化 driver**（`ScriptedTurnDriver`，确定性回放，零 API 调用）。

#### 链路构成

```
fake WeCom SDK client（记录每一条 stream 帧）
        │
WecomBotChannel（真实适配器：节流/stream/finish 语义都是真的）
        │
createServerReplyHandler → createMessageHandler（真实生产入口）
        │
createTaxAgentRuntime（真实：route_current_turn / 出口校验 / Context State / 记忆）
        │
createContextTaskRunner → createPiCodingWorkerSession（真实：G1 门 + 计划门）
        │
spawn 真 bin/17dz（DZ_EXECUTOR=mock：plan 账本/HMAC/累计/审计全是真逻辑）
```

只有两样是假的：**模型**（脚本化回放）和**平台执行器**（mock responder）。其余全真——包括企微投递语义、计划门禁、跨进程账本。

#### 场景矩阵

| # | 场景 | 输入 | 断言 |
|---|---|---|---|
| S1 | 旧答案不重放 | 先跑一轮真实查询，再发同一问题 | 第二轮产生新的 `plan evaluate` + 至少一次平台执行；回复文本 ≠ 第一轮；平台账本 `actual.calls` 增加 |
| S2 | 不给账套先追问 | "帮我查一下猫一杯的应收账款还有多少" | 用户收到追问；平台零调用；日志 `task_intent_route kind=clarify` |
| S3 | 旧范围不渗入 | 第一轮查幻辰，第二轮问猫一杯 | worker 收到的 `taskIntent.accountQueries` 不含幻辰；夹带旧账套的计划被 `PLAN DECLINED` |
| S4 | 扩范围先通知 | 单期查不通 → worker 提交 9 期计划 | 用户在扩范围查询**执行前**收到含"2026年01月至2026年09月"的通知帧；送达前平台查询失败；送达后成功 |
| S5 | 通知失败不执行 | 让 fake SDK 的 notice 帧抛错 | 用户收到失败话术；计划未激活；`plan current = none`；平台零扩展调用 |
| S6 | 高重量等确认 | worker 提交 21 期计划 + 自报 `userConfirmed` | 计划停在 `confirm`；未激活；用户被要求确认 |
| S7 | 确认后续跑 | S6 之后用户回复"确认继续" | 宿主激活计划、带 `resumeTaskId` 续跑**原 task**；回复来自本轮执行结果 |
| S8 | 旧计划被取代后确认 | 先提一个 confirm 计划，再提一个，然后对旧计划发"确认继续" | 明确告知已取代；不出现 generic"处理失败"；旧计划未被激活 |
| S9 | notify 次数上限 | worker 连续提交多个 notify 档计划 | 第 N 次升级为 `confirm`，需要用户确认 |
| S10 | 能力缺失明确拒绝 | 问账套是否存在（mock 种子无此账套） | 只调用 `finance.search-account-sets`；回复"未找到"；不用余额/凭证探测 |

S1–S3 对应 R1–R4，S4–S10 对应 R5–R10。**这些用例跑绿，7.4 的手测就只是抽查，不是主验证手段。**

#### 实现要点

- 每个用例独立的临时 `DZ_PLAN_STATE` / `DZ_MOCK_STATE` / `DZ_AUDIT_PATH` + `:memory:` SQLite，`afterEach` 清理。
- 平台根目录默认取同级 `../../17dz-platform`，`bin/17dz` 不存在才显式失败（不 skip）。
- 脚本化 worker 的每一步都要走**真实**的 `beforeToolCall` 门（`createPiCodingWorkerSession` 已经这么设计，provider 指向不可达地址但从不发请求）——所以 `PLAN DECLINED` / `PLAN STOP` / 参数错配都是真拦的。
- 断言分三类：**用户可见帧**（fake SDK 记录的）、**平台账本状态**（读 `plans.json` 或 `plan current`）、**结构化日志**（`task_intent_route` / `delegation_span` / `turn_span`）。
